# 设置页重构 v2 · 设计方案（原型评审稿）

> 触发：2026-11-11「重构下设置页面，现在看起来比较臃肿。数据这个地方折叠起来，并不是经常用的选项，帮我分下组。更新版本放到最下面，先出原型」。
> 配套原型：`docs/settings-redesign-v2-prototype.html`（单文件、无外链、可交互）。
> 设计基线：`docs/ui-redesign.md`「林间日志」token；现状代码 `feature/settings/SettingsScreen.kt`。
> **状态：已落地 Compose（2026-11-11）。** 六项决策按最小侵入取默认，结论见第 7 节；实机验收见第 6 节。

---

## 1. 诊断：臃肿从哪里来

对照当前 `SettingsScreen.kt`（5 个分区、13 行、两段长说明）：

| # | 现象 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | 分区随功能数线性增长 | `SettingsScreen.kt:323-548` 记录 / 数据 / 外观 / 安全 / 关于 五段顺次平铺 | 每加一项就多一段，用户要滚两屏才能到底 |
| 2 | 低频高破坏的备份操作常驻 | `:337-390` 导出 / 恢复 / 更换口令 3 行 + 状态行 + 红色风险提示，约 230dp | 一年用不了几次，却占掉首屏最显眼的一块 |
| 3 | 外观是「标题 + 三分段 + 说明」整块 | `:392-408`，与其它单行设置项不同构 | 一个只有三档的开关，视觉重量却和整段安全设置相当 |
| 4 | 「关于」混合四种频率的信息 | `:476-548` 版本 / 应用更新 / 更新日志 / 开源许可 / 数据与隐私 | 查版本、看许可、读隐私长文被塞进同一张卡 |
| 5 | 隐私说明是一整段长文 | `:518-547` 四段文字常驻（虽已折叠，入口仍在首屏中段） | 每次进设置都要路过一个几乎不点开的入口 |
| 6 | 版本号夹在「关于」中间 | `:477-487` | 「更新版本」既不在顶部也不在底部，找不到锚点 |

根因与 v1 相同但程度加深：v1 抽出了 `SettingsSection` / `SettingsRow` 统一了**排版**，但没有统一**信息优先级**。所有设置项仍然默认「平铺且同级」，功能一多就会重新变长。

## 2. 分层依据：使用频率 × 破坏性

|  | 低破坏 / 可撤销 | 高破坏 / 需谨慎 |
| --- | --- | --- |
| **高频** | 无标题主卡：记录项目、外观 | — |
| **中频** | 独立分组：安全 | — |
| **低频** | 二级页 / 页脚：更新日志、开源许可、数据与隐私、版本更新 | **默认折叠**：导出、恢复、更换备份口令 |

规则只有一条：**折叠的是「低频且高破坏」的操作，不是「不重要」的信息**。所以恢复行在展开后仍保留 error 色与「会替换当前全部记录」的文案，不能因为藏进折叠区就弱化警告。

## 3. 新信息架构

```text
设置
├─ [无标题主卡]          ← 进设置最常做的两件事，不加分区标题
│   ├─ 记录项目           已启用 4 / 共 5 项 · 启用与排序      >
│   └─ 外观               跟随系统 / 浅色 / 深色                >
├─ 安全                  ← 唯一保留的中频分组
│   ├─ 应用锁             [Switch]
│   ├─ 自动锁定           仅应用锁开启时出现                  >
│   └─ 截屏与录屏         状态直说「正常 / 已禁止」              >
├─ [独立卡] 数据与备份    ← 默认收起，展开在原地
│   ├─ 导出备份
│   ├─ 从备份恢复         error 色
│   ├─ 更换备份口令
│   └─ 风险提示           仅展开时可见
├─ 更多                  ← 只留只读 / 一次性入口
│   ├─ 更新日志            最近 6 个版本（有新版时显示标记）
│   ├─ 开源许可            弹窗
│   └─ 数据与隐私          就地折叠行
├─ [独立卡] 应用更新      ← 紧跟「更多」最后一行「数据与隐私」
└─ 页脚                  ← 整页最底部
    ├─ 生活记 0.6.4
    ├─ 本地生活记录工具 · 不提供医疗诊断
    └─ [有新版时] 应用更新卡内展开更新提示
```

分组理由：

- **「记录 / 外观」合并且不加标题**：这是两个最高频项，标题在这里是噪声；视觉上用「第一张卡」表达默认层级，比加一个「常用」标题更轻。
- **「数据」改名「数据与备份」**：原分组名会被误读成「统计 / 记录数据」，实际里面全是备份操作。改名后折叠行的摘要「导出、恢复与更换口令」与内容一致。
- **「安全」独立保留**：找应用锁的人不会先去数据区翻；且这一组的状态（已开启 / 已禁止）需要随时可查，不适合折叠。
- **「关于」拆散**：版本 → 页脚，隐私 / 许可 / 日志 → 「更多」，原来的分组名不再承担信息归类，直接删掉。

## 4. 三条关键决策

### 4.1 数据与备份折叠

| 项 | 规则 |
| --- | --- |
| 默认状态 | **收起**。只暴露一行：图标 + 标题 + 摘要 + 向下箭头 |
| 展开方式 | 原地展开，不跳页、不弹窗（保住用户当前滚动位置与任务上下文） |
| 展开内容 | 3 个操作行 + 分隔线 + 红色风险提示，顺序不变 |
| 摘要文案 | 「导出、恢复与更换口令」——不看内容也知道里面有什么 |
| **状态外溢** | 导出 / 恢复进行中或刚完成、发生失败时**自动展开**，不能把 `status` / `failure` 藏在折叠区里 |
| 持久化 | **建议不记住展开态**。低频项下次进来仍收起，避免用户某次展开后页面永久变长 |
| 动画 | 300ms `cubic-bezier(.2,.8,.2,1)`；系统「移除动画」时降为瞬时 |

> 最后一条「状态外溢」是落地的硬约束。现状 `SettingsScreen.kt:374-385` 的状态行、`SettingsScreen.kt:1069-1077` 的失败弹窗都挂在数据区，折叠后若不同步展开，用户会看到「点了导出但什么都没发生」。

### 4.2 按频率重新分组

- 分区从 5 段收敛为 **2 个带标题的分组（安全 / 更多）+ 2 张无标题卡 + 1 个页脚**。
- 分区标题保持 `11.5sp / 600 / +0.6sp 字距`，不与正文抢层级；`heading()` 语义保留。
- 首屏（412×844 设备）可见：主卡、安全、数据与备份折叠行、更多。整页高度按行高估算约 **790dp**，对比改前约 **1700dp**，页面长度减少约 54%（估算值，用于相对比较，非 dp 实测）。

### 4.3 检查更新紧跟内容区，版本号沉到最底

- 「应用更新」从「关于」中部移出，作为**独立卡紧跟「更多」分区**（其最后一行是「数据与隐私」）；版本号与「不提供医疗诊断」免责文案才放在整页最底部。落地初版曾把卡片排在版本号文字下面，验收时被指出与原型不符，已调整（2026-11-11）。
- `BuildConfig.VERSION_NAME` 是唯一数据源，原型里的 `0.6.4` 只是 mock。现状「版本」行的免责文案是合规要求，**随页脚保留**，不因精简丢失。
- 有新版时应用更新卡内展开 `UpdateAvailable`；**状态机沿用 `UpdateSection.kt` 的 10 态**（Idle / Checking / Preparing / UpToDate / Pending / Available / Downloading / Verifying / Ready / Error），尤其 `Pending`（安装包同步中）与 `Error` 不能被简化成一张静态卡。
- **可发现性兜底**：折叠态下页脚落在首屏下沿之外约 90dp，需轻扫。因此有新版时，首屏「更新日志」行同步出现「有新版本」标记并把副标题改为「vX.Y.Z 已发布 · 向下查看更新」。下沉不等于藏起来。

### 4.4 更新日志只列最近 6 个版本

- `versionHistory` 保留全量数据（发版时在最前面补一条的约定不变），**弹窗展示层**用 `take(6)` 截断，并在末尾注明「仅显示最近 6 个版本，完整历史随版本累积」。
- 落地初版沿用现网的全量渲染，0.1.0–0.6.4 共 10 条全上屏，验收时被指出与原型（6 条）不符，已修正。
- 「更新日志」入口副标题同步改为「最近 6 个版本的变更」，避免文案与内容不一致；原型 HTML 的页脚顺序与文案也一并同步。

## 5. 组件与视觉规格

| 组件 | 规格 |
| --- | --- |
| 设置行 | 最小高 56dp；20dp 图标（大字号下 Top 对齐）；标题 16sp / 摘要 12.5sp；`heightIn` 而非固定 `height` |
| 分隔线 | 从文字起始处缩进 16dp，`outlineVariant` 50% |
| 卡片 | 圆角 16dp，`surface` 底；深色下补 1dp 极淡描边 |
| 折叠行 | 整行 `Role.Button` + `aria-expanded` 等价语义；箭头旋转 180°；读屏念「展开备份选项 / 收起备份选项」 |
| 标记 | `primaryContainer` 底 + `primary` 字 + 6dp 圆点，11sp；不参与默认布局（`display:none` → `inline-flex`） |
| 页脚 | 版本号用等宽数字；「检查更新」与「更新」按钮最小触摸目标 **48dp**（原型已从 40 / 38px 上调） |
| 二级页 | 56dp 顶栏、48dp 返回箭头、页面从右侧 300ms 滑入；与现有 `ModuleManagementScreen` 同构 |
| 状态可读性 | 所有状态用文字直说（已开启 / 正常 / 已禁止），颜色只作辅助；正文对比度 ≥ 4.5:1 |
| 动效 | 折叠 300ms、二级页 300ms、弹层 260ms；`prefers-reduced-motion` 下全部瞬时 |

组件规格沿用现有 `SettingsSection` / `SettingsRow` / `SettingsDivider` / `SettingsNote`（`SettingsComponents.kt:46-157`），原型没有引入新的排版参数；新增的只有折叠容器、页脚与标记三件。

## 7. 与原型的差异 · 落地结论

用户「开搞」批准落地，按**最小侵入**取默认；验收时又针对「应用更新位置」与「更新日志条数」提出两处修正，均已回改并同步原型 HTML。

| # | 原型 | 落地结论 |
| --- | --- | --- |
| 1 | 外观：单行 + 弹层三选一（radio） | ✅ 单行 + 弹层，但复用现网 `ThemeModeRow` 三分段，保住 200% 字号与「系统」缩写适配 |
| 2 | 数据与隐私：独立二级页 | ⚠️ **保留就地折叠行**，只移到「更多」；改二级页要动导航路由，对减臃肿无收益 |
| 3 | 更新日志：滑入二级页，列 6 条 | ⚠️ **保留弹窗**，只移到「更多」；✅ 条数已按原型截断为 6 条并加说明 |
| 4 | 折叠态不持久化 | ✅ `remember` 状态，下次进来仍收起 |
| 5 | 检查更新在页脚版本号下方 | ✅ **验收修正**：应用更新卡紧跟「数据与隐私」，版本号与免责文案沉到整页最底部 |
| 6 | 有新版时页脚换提示卡、首屏标记兜底 | ✅ 不镜像顶部提示，用 `UpdateBadge` + 副标题兜底 |
| 7 | 「截屏与录屏」状态行 | ✅ 原样保留（落地另带一段常驻说明，原型没有） |

> 仍未对齐的三处：数据与隐私 / 更新日志的交互形态（折叠行 / 弹窗 vs 二级页）、「更多」三行顺序（落地沿用原「关于」顺序）、安全区多出的一段常驻说明。如需完全对齐原型，单独开一轮即可，不影响信息架构。
