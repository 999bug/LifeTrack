# 架构演进与可维护性优化

> 日期：2026-11-19。状态：已批准（用户要求“建立子任务 逐个完成”）。

## 1. 背景与目标

当前应用已具备成熟的 Local First 数据链路、Room 迁移测试、加密备份和发布流水线。主要维护风险不在框架选型，而在应用层状态持续集中、页面职责过重、日期源分裂以及自动化测试覆盖不足。

本轮按可独立验收的子任务逐步演进，目标：

- 首页、历史、月历、统计、经期和运动使用同一个“今天”来源，跨午夜与回前台后保持一致。
- 把设置页的备份编排从 Compose 中抽出，降低单文件状态数量。
- 按页面 / 领域逐步拆分 `MainViewModel`，移除 feature 间通过 home 包互相依赖。
- 为写操作建立统一的成功与失败反馈通道。
- 收敛 `domain` 对 Room 实体和投影的直接依赖。
- 把新增记录类型需要的注册信息收敛到可测试的注册表。
- 历史记录采用有上限的分页查询。
- 补齐 ViewModel / Compose 测试，并让设备测试成为稳定门禁。

## 2. 非目标

- 不更换 Compose、Room、DataStore、SQLCipher、Coroutines 或 Navigation 框架。
- 不升级 AGP、Kotlin、Gradle、Room 等大版本。
- 不修改 Room schema、备份格式、统计口径或现有用户数据。
- 不在本轮拆成大量 Gradle feature 模块；先建立包内边界和测试。
- 不引入 Hilt、Koin 等 DI 框架。
- 不改 `applicationId`，避免破坏已发布版本的覆盖升级链路。

## 3. 方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 单模块内渐进拆分职责，先修正确性再拆状态 | 风险低、每步可验证、保留现有数据链路 | 需要多轮小改动 | 采用 |
| B. 全量重写为严格 Clean Architecture | 理论上边界清晰 | 范围大、容易改变行为、验证成本高 | 不采用 |
| C. 引入多模块 + Hilt 一次性重构 | 强制边界、长期扩展性好 | 当前规模收益不足，构建和迁移风险高 | 暂不采用 |

## 4. 设计约束

- 每个子任务独立提交，提交前跑对应单测、lint 和构建。
- 外部行为变化必须来自明确的问题修复；纯重构保持行为不变。
- 数据安全、备份兼容、应用锁和更新链路不得因结构拆分改变。
- 新代码的日志与异常消息用英文，注释和文档用中文。
- 先保留现有公开入口，逐步迁移调用方，避免一次性大爆炸式改动。

## 5. 验收标准

- 跨午夜、跨时区和回前台后，首页、历史、统计使用同一业务日期。
- `SettingsScreen` 不再直接管理完整备份状态机。
- 非 home feature 不导入 `feature.home.MainViewModel`。
- feature 不直接导入 `core.database.*`。
- 写操作失败有用户可见反馈。
- 新增记录类型所需修改点集中且完整性有测试保护。
- 历史查询每次最多返回固定页大小。
- 关键 ViewModel 流、页面主路径和设备测试有自动化覆盖。
